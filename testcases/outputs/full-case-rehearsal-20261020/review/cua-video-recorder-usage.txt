Encoding/format evidence
- Only app.getScreenshot({emit:false}):Promise<Uint8Array> is called.
- Existing files named .png are actually JPEG/JFIF; detect actual magic bytes.
  PNG input uses image2pipe/png; JPEG input uses image2pipe/mjpeg. Screenshot
  bytes stream directly, without per-frame transcoding or PNG archives.
- ffmpeg uses input use_wallclock_as_timestamps=1; image timebase1ms via
  framerate1000; copyts/start_at_zero; output enc_time_base1:1000/fps_modevfr.
  x264 fps=<requested>/1:force-cfr=0 keeps the H264 codec level ordinary (the
  tiny test is ConstrainedBaseline level4.0). No output -r, synthetic frames,
  native renderer or OS capture. Container nominal rate may still say1000;
  actual variable packetPTS and capturecount are the timing evidence.
- H264 ultrafast/yuv420p in MKV, flushed packets, <=1s target clusters.
  Prior clusters are recoverable after an abrupt failure; final footer/cluster
  may be incomplete. Graceful stop is the expected completion path.
- First captured frame fixes even outputdimensions. Later window-size changes
  are scaled/letterboxed to those dimensions, not cropped. Keep window stable.
- PTS is ffmpeg's actual demux-read clock, not the precise instant pixels were
  captured. JSONL records capture begin/end UTC+monotonic timestamps, streaming
  backpressure, UI intervals, counts, errors and the exact encoderarguments.
  Initial encoderstartup caused about0.12s offset in the tiny test; warm/probe
  before clicking Play. Large backpressure or screenshotduration can shift PTS
  relative to capturetime; inspect receipts rather than asserting exact2fps.
- Root should ffprobe completed output: codec h264, monotonic VFR packetPTS,
  framecount consistent with encodedInputFrames, duration comparable to capture
  interval. ffmpeg error exit/nonzero errorcounts invalidate completion claims.
