Diagnostic transfer lifetime repair — source candidate ready

Cause confirmed by source: import_diagnostic_layer creates two BinaryTransfers
snapshots and returns their descriptors, but neither snapshot belongs to an
existing prune root. BridgeRuntime._work emits the result and then unconditionally
calls session.prune_transfers in finally. The previous Bridge regression waited
for completion but inspected descriptor metadata without opening the returned
files, so it did not detect this lifetime failure.

Minimal production change
- _CaseEntry retains diagnostic_transfer_paths, an internal tuple of exactly the
  latest diagnostic's state and coverage paths. No arrays/results are added to
  CaseData, saved workspace fields, source descriptors, actor or planning inputs.
- prune_transfers includes those paths for each still-cached case. Replacing a
  diagnostic overwrites the tuple, allowing ordinary finally pruning to remove
  old unshared files. Existing content-address sharing remains respected.
- Both same-hash _install_case replacement branches reset the tuple. A new case
  starts empty; LRU eviction and session close naturally release its retention.
- After validation and both snapshot writes, the importer uses the existing
  request.begin_commit gate before replacing the tuple. Cancellation before this
  gate preserves the previous tuple; existing runtime finally pruning discards
  new uncommitted files. After the gate, the established request contract refuses
  cancellation through the small assignment/publication commit.

Bound: latest result only per cached case, independent of attachment count: at
most two one-byte-per-voxel files under the unchanged 64-Mi-voxel importer bound
(128 MiB per case before content-address sharing). Only paths are retained in
memory. No new persistence, registration, source admission or scientific claim.
