# Matched 64³ stage-zero recomputation: actual generated pair audit

**Numerical gate PASS; no robust performance claim.** Root ran one hook-free baseline, then one recompute arm under frozen contract SHA-256 `df13db40de28b9782dc7b5e3110538b7b4671aaefec2249d6a57977bbfc9d4b2`. I audited only saved generated arrays, receipts and source hashes; I did not read the checkpoint or run a model. The initial comparator call with invalid mode `recompute` refused before reading arrays or writing comparison; the documented `pair` mode ran once and is the accepted saved comparison.

Both output arrays are finite C-contiguous FP32 `[1,3,64,64,64]` and byte-identical: NPY SHA-256 `377bb7a1dc0bea971ab3c2890432d20c2230744b479a5e7605bd824b0a81ddb1`, raw SHA-256 `52252550d12d7fc0ddd930c044f58cd6e1bca00606646bbd9780687bce3f2853`. The prospective `atol=rtol=0.001` continuous gate passes with maximum error zero and zero sequential decoded-label disagreements. The baseline also equals the accepted V4 historical output. Source hash closure remained 18/18, with the generated input and tracked tiled adapter unchanged. The result records unchanged strict-load alias checks (88 groups, 184 pairs), 27 unique tiled Conv3d wrappers, five lazy decoder stages, no dense hooks, full-feature-map InstanceNorm, and recompute attachment only for the second arm. The recompute result reports one released early skip and one decoder-triggered recomputation; the underlying code enforces these conditions on the successful forward.

Each arm passed its own 30-second preflight. Baseline/recompute completed in 2.633/2.474 seconds with exit 0, `accepted_for_feasibility=true`, no watchdog/post-guard reason, and clean identity-bound finalization. Baseline had 46 fast and 6 slow samples; recompute had 43 fast and 5 slow. Both maintained kernel pressure mask 1, zero swap-used growth, no blocking project overlap, and exact live IXI and Tracto identities. Minimum available memory was 47%/48%; maximum fast sample gap was 0.060/0.061 seconds. Recomputed sampled process-group RSS peaks match receipts exactly: 759,906,304 bytes baseline and 723,419,136 bytes recompute, below the 3 GiB cap. Neither finalizer records residual group/detached processes or cleanup errors.

The recompute peak was **36,487,168 bytes (34.80 MiB, 4.80%) lower** in this one ordered pair. But recompute already used **16.73 MiB less before forward**; subtracting each arm's own pre-forward RSS leaves an 18.06 MiB difference in peak forward increment. RSS was sampled at roughly 20 Hz and the arms ran sequentially on a shared host, so the observed difference cannot be confidently attributed to skip recomputation. Forward time was 0.615 seconds versus 0.542 seconds baseline (+13.3% for recompute). These are exploratory single-run observations, not evidence of a dependable memory saving or speedup.

The result supports exact numerical parity on this single generated smaller-than-training-patch input. It does not establish 128³ feasibility, patient-specific performance, clinical validity, or transfer beyond this network/input/runtime. The existing full128 pressure-stopped negatives remain unresolved.
