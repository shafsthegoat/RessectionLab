## Concrete guard gap

The attachment checks stage-zero block structure and preexisting hooks, but does not pin the types/forwards and input-mutation behavior of encoder stages 1 through the last stage. A later stage can mutate the original stage-zero output after computing its own output. In the baseline, the decoder then consumes this changed retained skip. In the recompute wrapper, the decoder receives a fresh stage-zero output from the unchanged original input, so logits differ even though the wrapper accepts the graph.

I saved a tiny generated reproducer at `build/scan-target-estimator-independent/recompute-skip-stage1-mutation-counterexample.py` (SHA-256 `c39dfd9e54e5c823ceed47e3fe2ebfe7088bbf67d498bb870277a6aa2c5c9172`). It wraps stage one with a module that runs the normal stage and then adds `0.25` to its input. There is no training mode, dropout, hook, checkpoint or patient input. The current `attach_recomputed_stage_zero(..., expected_encoder_stages=3)` **accepts** this graph, but the fixed-seed generated logits are not exact (maximum absolute difference `0.2640131`). This does not imply the actual pinned six-stage GlioMODA graph contains such a mutation; it shows that the present guard cannot prove the claimed graph purity before attaching to it. The initial `RESULT.md` phrase that controls reject “stateful/custom/hooked graphs” is too broad; the tests cover specific stage-zero changes and hooks present at attachment.

The proposed trained branch requires the already-reviewed lazy decoder source and a bound five-stage decoder forward, but has not been exercised with that proxy at six encoder stages. Nor does it constrain hooks added *after* attachment. The provided tiny test itself adds passive hooks after attachment, and another test adds a post-attachment hook that raises on the second stage-zero call. In a future instrumented model, observer hooks must be explicitly pinned as passive and stage-zero events counted twice; arbitrary later hooks could mutate or retain data and defeat the release claim. The original input also remains retained until decoder use, so any memory gain is a trade against that retention and a second stage-zero compute pass, not a guaranteed peak decrease.

The smallest sound next revision is to fail closed on the exact downstream encoder stage types, forwards and operator order for the pinned constructed network, including a proof they do not mutate stage-zero input; explicitly bind the allowed observer-hook contract and input ownership; then add a generated six-stage lazy-decoder test with exact logits, state/alias identity, and repeated-call counts. Only after that should a separately guarded full-network memory control be proposed. Keep a prospective numerical rule and resource cap fixed before any trained-network run.
