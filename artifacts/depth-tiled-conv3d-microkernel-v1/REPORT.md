# Generated-only Conv3d output-depth tiling: bounded operator proof

The frozen Gate A v3 CPU control is a negative result: its child reached the generated forward, then actual macOS kernel memory-pressure mask changed from normal `1` to warning `2` while sampled child RSS had reached 1,428,946,944 bytes. The controller stopped it after 2.064 s elapsed; there are no completed logits. Neither MPS nor the 128³ production patch is admitted by that result. The V3 guard and receipt are not modified here.

The pinned GlioMODA nnU-Net `3d_fullres` plans specify `torch.nn.Conv3d` with six stages, 3×3×3 kernels, strides 1 then five depth/height/width strides of 2, and features `[32,64,128,256,320,320]`. The installed `dynamic_network_architectures.building_blocks.simple_conv_blocks` constructs these with padding `(kernel-1)//2`, dilation 1, `conv_bias=true`; groups default to 1. This is metadata/source inspection only, with no checkpoint deserialization or model forward in this work.

`depth_tiled_conv3d.py` computes each requested output-depth slab from exactly the input depth interval covering its full receptive field, including explicit zero boundary padding. It calls the installed native `torch.nn.functional.conv3d` on the slab with unchanged weight, bias, stride, height/width padding, dilation and groups, then places the tile into a preallocated full output tensor. This is CPU/FP32 inference-only. It preserves the full output tensor for later InstanceNorm statistics; tiling an entire ConvNorm block would not preserve those statistics.

Six generated tests covered the pinned stride-1/stride-2 geometry, edge tiles, asymmetric stride/padding, dilation, grouped convolution, and one-output-depth tiles. All shapes and values were exactly equal to native Conv3d (max absolute error 0). An initial `python -I` test launcher failed before import because isolated mode removed the sibling module from `sys.path`; the corrected pinned-venv invocation passed. No test used model weights or patient records.

A separately bounded generated microkernel used input `[1,16,32,48,48]`, weight `[16,16,3,3,3]`, padding1, stride1, dilation1, groups1 and tile output depth4. Each mode ran in its own child under a 1 GiB sampled-RSS / 30 s / normal-kernel-pressure guard. Both exited0 with normal pressure and ≥51% available memory. Full saved FP32 output arrays matched bit-for-bit; both raw SHA-256 hashes are `b857b0f905f731797987ee74d04c9fcdb701f382e9aab850e32d8c423e9015a7`, with zero `rtol=atol=1e-3` violations. Native sampled peak RSS was 351,387,648 B (process `ru_maxrss` 351,289,344 B), versus tiled 241,319,936 B (`ru_maxrss` 241,221,632 B). One forward took 22.38 ms native and 10.11 ms tiled. The RSS difference is real for this generated operator case; the single-call timing is exploratory and not a model-speed claim. These peaks include Python/Torch baseline, so the approximately 110 MB delta is an operator-case measurement, not a guaranteed reduction at network scale.

The next decision depends on independent review of this operator and saved outputs. A prospective **new** generated network control could use `[1,2,32,32,64]` (five stride-2 levels leave 1×1×2 at the deepest InstanceNorm, above its one-element failure case) to compare the exact pinned weights under native Conv3d and a patch that substitutes only Conv3d calls with output-depth tiling. It would keep full FP32 logits, unchanged normalizations, and the existing `rtol=atol=1e-3` plus exact decoded-label criterion. It would require a new frozen resource/host contract and two separately counted calls; this operator proof does not authorize those calls. The original `[1,2,32,64,64]` Gate A and 128³ production-patch questions remain unresolved, and no patient inference is implied.
