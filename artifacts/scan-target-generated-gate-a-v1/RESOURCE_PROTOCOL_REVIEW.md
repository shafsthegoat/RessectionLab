No logits or MPS child exist. These numbers are in `build/limited-input-guard-design/gliomoda-mps-gate-a-v1/cpu/{host-preflight,supervision}.json`; the independent receipt audit is `build/scan-target-estimator-independent/mps-gate-a-cpu-negative-audit.md`. Preserve this as a negative resource outcome, with no retroactive relabeling or retry of v1.

The occupancy jump coincided with the worker's forward phase, but the signal is **system-wide** and the saved receipt contains no full concurrent-process timeline or kernel pressure-level series. The HBE agent reported no FEBio native run or new replay supplement at that time; it did run a 22.31-second pytest suite around this period, but has neither exact start/end times nor RSS. Overlap and contribution are unproven. A file-mtime scan and a preflight filter for processes ≥512 MiB cannot exclude concurrent work below that cutoff. We cannot attribute the entire 892 MiB to either process, nor establish whether the OS was in normal, warning, or critical state at the stop.

## What the macOS indicators mean

Apple's [`memory_pressure` source](https://github.com/apple-oss-distributions/system_cmds/blob/main/memory_pressure/memory_pressure.c) prints “System-wide memory free percentage” from `memorystatus_get_level`; [XNU's implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_memorystatus.c) copies out `memorystatus_level`. This is a system-wide *available-memory percentage indicator*, not literal idle physical RAM and not the categorical VM pressure state. Locally, `sysctl -n kern.memorystatus_level` and `memory_pressure -Q` both returned 50 at one later read. The local manual omits `-Q`, but the installed command and Apple's source support its read-only use with no allocation options.

The separate `kern.memorystatus_vm_pressure_level` sysctl returns a **dispatch mask**: [`event_private.h`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/event_private.h) defines **1=normal, 2=warning, 4=critical**; [`kern_memorystatus_notify.c`](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_memorystatus_notify.c) converts internal levels 0/1/2/3 to those masks before returning the sysctl. Thus a later observed sysctl value `1` means **normal**, not internal “warning=1.” [XNU's memorystatus note](https://github.com/apple-oss-distributions/xnu/blob/main/doc/vm/memorystatus_notify.md) defines the levels and explains that compressed pages remain partly reclaimable. [Apple's Activity Monitor guide](https://support.apple.com/guide/activity-monitor/view-memory-usage-actmntr1004/mac) says macOS compresses inactive app memory to make RAM available and evaluates pressure using multiple factors including swap rate. Compressor-occupied growth **alone** therefore neither proves dangerous pressure nor proves harmlessness. The sysctl is a sampled instantaneous state; it can miss a short excursion between samples. The current main-branch XNU source documents semantics, but the recorded v1 experiment did not sample that sysctl, so its past state is unknown.

## Bounded v2 design for independent review before execution

1. Keep v1 intact and declare a new v2 run ID/script hashes. Use exactly one generated-only, asymmetric `[1,2,32,64,64]` FP32 CPU call first, identical checkpoint and numerical contract. No patient arrays, full-volume inference, 128³ call, or automatic retry. Only consider a separate MPS child after the CPU control succeeds and its resource trace is independently reviewed.
2. Serialize this short control with other project compute: the coordinator announces an exclusive window; defer if HBE pytest/FEBio, acquisition postprocessing, model tests, or another heavy project job is active. Timestamp a project-process inventory before, during, and after the call (PID, PGID, command class, RSS) with no ≥512 MiB-only blind spot. Never terminate user applications. If overlap appears or host samples cannot be parsed, mark the run **HOLD**, even if logits are finite.
3. Preflight for ≥30 seconds at 5-second intervals: require kernel sysctl mask **1 (normal)** at every sample, `memory_pressure -Q` ≥45% at every sample, and nonincreasing `vm.swapusage used`. The 45% figure is the *existing project headroom rule*, not an Apple safety threshold. Record `vm_stat` page size, compressor-occupied pages, swapout/pageout counters, plus the current process inventory. If any reading fails or a warning/critical mask occurs, defer without a child.
4. During the child, sample at ≤0.2-second intervals. Keep unchanged independent **3 GiB process-group sampled RSS** and **120-second wall-time** limits; for any future MPS child, apply the previously reviewed nonzero allocator cap before allocating an MPS tensor and collect `current_allocated`/`driver_allocated` separately. Do not add RSS to Metal bytes. Stop on sampled kernel **warning (2) or critical (4)**, unknown mask or failed parser, `memory_pressure -Q` **<30% or >20-point fall** from accepted baseline, `vm.swapusage used` **>128 MiB growth** from baseline, RSS cap, MPS cap, or timeout. The free/swap numeric limits are retained *predeclared conservative project stops*, not OS-defined unsafe thresholds. If a new swapout/pageout trend arises without an existing stop, mark **HOLD for review**, rather than calling the host healthy by percentage alone.
5. Record compressor occupancy and its time derivative as **diagnostics**, not an automatic +256 MiB stop. That specific v1 stop had no physical or XNU threshold basis and triggered while the other recorded indicators had not crossed their limits. The proposed change follows indicator semantics; it does not convert v1 to a pass. Retain first-failure receipts and no automatic cap increase. A v2 CPU pass would establish only a generated-input numerical control; the MPS parity and 128³ production-patch questions remain separate gates.

The v2 guards remain sampled and cannot guarantee that a 16 GiB shared-memory Mac never experiences a brief pressure spike. The strong claim available from a completed v2 is bounded resource use under its observed conditions. The stop/hold policy should be frozen and independently approved *before* the next call.
