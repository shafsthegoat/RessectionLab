# Independent source review: Case4 DEVELOPMENT diagnostic handoff V1

**Decision: HOLD patient-connected promotion/release.** The candidate is currently unlaunchable as intended: `CASE4_FORWARD_RELEASE_SHA256=None` makes accepted-output decoding refuse, and `model_backend/pair-contract.json` is absent. This source review did not open patient image arrays or weights or run a model.

The five small Case4 manifest/preparation/support/supervision JSON files exactly match the hard-coded receipt SHA-256 pins. Their checked status remains DEVELOPMENT, geometry/support-only, unqualified anatomy, unknown training overlap, and no planning admission. The worker's network construction, safe scoped weight load, 27 tiled convolutions, lazy decoder and stage-zero recomputation are unchanged in the reviewed numerical span relative to the accepted generated full128 V3 backend; its changes are Case4 input/gate/lineage metadata. The supervisor retains the identity-bound launch/finalizer and requires the prior 3 GiB RSS, 120-second wall, 30-second preflight, pressure/free/swap/overlap stops before any future release. `monitor_primitives.py` differs from V3 only by docstring and corrected repository-root depth. The copied helpers are otherwise unchanged except the launch-gate docstring. This verifies source lineage, not patient numerical behavior.

Three handoff gaps need correction before a patient-facing forward/output release:

1. `decode_model_output` checks the accepted input raw hash supplied by its caller, but never compares the passed `prepared` object's scan/support hashes, atlas affine/shape, crop or patch start against that accepted input receipt. A legitimate Case4 output could therefore be decoded onto a different prepared frame. `write_display_artifact` likewise accepts an arbitrary 64-character input-receipt digest without binding it to the prepared object. Bind a trusted input-receipt hash plus exact geometry/source fields through `read_accepted_forward` and require equality at decode and display writing.
2. `write_display_artifact(..., accepted_forward=None)` labels any supplied arrays `generated_control_no_patient_or_model`. It does not prove they are generated, so a caller can pass patient-derived `prepared`/`display` data and produce a falsely labeled generated artifact. Separate a generated-only control writer from the Case4 writer or require an explicit, verified generated provenance; patient-derived data must fail closed without the pinned forward receipt.
3. `write_model_input` accepts manually constructed `Case4Bindings` and checks consistency only against `prepared.geometry`, not whether those bindings came from the exact pinned Case4 receipt chain. Its test intentionally constructs such bindings for generated data. Before a real Case4 handoff, require a trusted evidence-chain marker/factory or reverify the five pinned receipts and exact source bytes at the write boundary. The future contract must pin the resulting input receipt/source/frame/patch identity, not merely self-consistent caller hashes.

`read_accepted_forward` also reads result/supervision JSON without fixed content hashes. In a future release, require the supervisor's contract digest/arm/result existence and accepted closeout fields to match the pinned contract and bind the final output receipt independently; current checks of exit, guards, cleanup and output hashes are useful but are not an independent provenance anchor by themselves. Review the complete future resource contract against accepted V3, including fields not checked as literals in the supervisor. These are prospective release requirements; no patient forward is presently possible from this folder.

The proposed TypeScript layer is distinct from planner `CaseData`, preserves unknown state and `planning_eligible=false`, and has no desktop integration yet. A completed model forward here would remain one unreviewed Case4 patch, without tumor annotation, full-volume coverage, held-out evaluation or clinical validity.
